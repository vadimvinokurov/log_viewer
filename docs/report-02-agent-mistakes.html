Каталог паттернов

P7 · Убегающие агенты — крупнейший отдельный паттерн агент

Что: после появления токен-правил (утро 11-24) размеры агентов выросли 5×: 628 k / 578 k / 385 k / 361 k / 327 k токенов против диапазона 44–85 k в предыдущий день. Один UI-агент 21+ минут наблюдал за собственным фоновым запуском бенчмарка, платя весь свой контекст за каждый опрос. ≈2.65 M субагентских токенов только за 11-24. Причина: в промпте не было капы; ожидание/мониторинг припаркованы внутри долгоживущего агента. Цена: крупнейшая биллинговая корзина проекта.

есть правило 7 («ограничивать агентов и ставить чекпойнты») — сработало как проза. новое (a) явная строка бюджета в каждом spawn-промпте («≤ ~120k токенов / ≤ 60 вызовов; у лимита → чекпойнт через bd update --notes и стоп»); (b) мониторинг фоновых задач — работа координатора, никогда не долгоживущего агента.

P1 · Слепота к токен-бюджету до убийства 429 агент

Что: 16 убийств по лимитам в трёх сессиях; два агента умерли посреди задачи с <20 k частичных расходов; 11-25 недельный лимит заморозил сессию, и владелец шесть раз тыкал её «продолжи», прежде чем что-то ответило. Причина: чекпойнты ставились на рубежах, никогда перед самыми дорогими шагами (полные гейты, бенчмарки) — ровно там, где убийство болит сильнее всего.

есть правило 7 (кап и чекпойнты агентов). новое чекпойнт-перед-долгим-гейтом: перед любым полным гейтом воркспейса / бенчмарком / большим прогоном e2e — bd update --notes и объявление ожидаемой длительности. Стоп без заметки о возобновлении — отдельный класс багов (см. P8).

P5 · Отладка путём shell-эскейпа в файлы агент

Что: борьба с driver.rs (5–6 безуспешных раундов python-heredoc, «десятки тысяч токенов», инструмент Write решил с первого раза); тот же паттерн всплыл снова уже после правила 7 — сломанный macOS sed -i и 14 подряд heredoc-правок live_check.mjs 11-24/25. Причина: привычка; один только текст правила дважды не сработал.

есть пункт правила 7 + ловушка в agent-brief. новое postToolUse-хук, считающий Bash-мутации файлов (sed -i, heredoc-редиректы, perl -pi, tee file) и блокирующий третью с текстом «используй Edit/Write / перезапиши файл». Самый дешёвый механический выигрыш в ките.

P2 · Поздняя верификация — CI ловит то, что пропустили локально агент

Что: v0.2.0 (11-25 07:16): тег отправлен, CI-прогон tsc -b поймал две ошибки типов, которые vitest видеть не может (esbuild срезает типы), потому что локальные гейты прошли со стейл tsbuildinfo-кэшем и без свежего tsc -b. v0.1.0 накануне уже перетегивалась дважды (антиалиасинг- nondeterminism golden; недостающие GTK-библиотеки на ubuntu). Причина: агент прогонял приблизительное подмножество гейтов и считал зелёный vitest покрытием типов.

есть правило 9 + PIPELINE §6a. новое scripts/release_gates.sh, запускающий точную CI-последовательность (сначала стирание tsbuildinfo), — единственный санкционированный путь к тегу, плюс pre-push хук, проверяющий, что последний зелёный прогон скрипта новее коммита тега.

P4 · Отладка наррацией вместо измерения агент

Что: набор e2e застрял; первый ответ — уверенное объяснение «это не висит, а медленно работает». Одна проверка таймстампов позже: старый набор занимал 14 секунд, а state 33 навечно блокировался на не-разрешающемся промисе downloadAndInstall. Плато e1/e3/e6 live-check два раунда трактовалось как «поведение скролла», прежде чем был доказан пер-пробный обход counts. Причина: теория до доказательств.

есть superpowers:systematic-debugging. новое жёсткий пункт: когда прогон превышает ожидаемую длительность в 2×, первым действием является замер с таймстампами (маркеры прогресса), никогда объяснение; без числа недопустимы объяснения «это просто медленно». Расширение «чисел вместо скриншотов» на длительности. Расширение «чисел вместо скриншотов» до длительности.

P6 · Разбухание промптов агентов — спека декодирована 9+ раз агент

Что: ранние промпты пересказывали семантику спеки inline и указывали на 4–6 файлов «прочти первым»; каждый агент сам заново декодировал конвенции (это дублирование также породило класс бага с импортами разного регистра). Исправление уже доставлено: docs/notes/agent-brief.md — промпты сжались с ~1 k токенов до ~30 строк, и это лучшая подтверждённая экономия на сегодня.

есть правило 7 + agent-brief. новое скил кита «общий-Agent-Brief»: шаблон (где правда / жёсткие ограничения / конвенции / spawn-контракт / ловушки) + smell-тест «spawn-промпт длиннее ~15 строк означает, что недостающий контекст идёт в brief, а не в промпт».

P8 · Мёртвый эфир — немые остановки и пустые ответы общая

Что: после лимитных убийств сессия выглядела подвешенной — «чет встал агент походу», «чет висло все»; два буквальных пустых ответа «no response» на пинг владельца; собственное распоряжение «ты продолжай работу, не останавливайся пока не закончишь» против агента, остановившегося раньше. Причина: остановки без видимой пользователю статус-строки. Примечание: это координаторское поведение — каждая остановка имеет одну строку: сделано / жду X (id) / возобновится на бисесе Y.

новое правило кита: статус-при-стопе для каждого агента и координатора; немая остановка немедленно переоткрывается. Дёшево, высокая ценность для доверия владельца.

P3 · Доверие заявлениям о завершении без артефактов общая

Что: агенты отчитывались «все гейты зелёные», в то время как milestone live check три прогона подряд проваливался в реальном окне (viewport anchoring, позже найдено: per-probe обход counts); оценка спеки «6.4M строк» жила в доках, пока первый бенчмарк не измерил 1,294,246. Причина: зелёные тесты отождествлялись с завершением.

есть правила 4–5, bd acceptance = команды. новое поле spawn-шаблона: каждое «done» несёт результаты гейтов (команда, счётчики, коды выхода); голое «всё зелёное» приравнивается к не-отчёту.

P9 · Текучесть требований вокруг дизайна владелец

Что: >20 микроправок по скриншотам за ~1.5 ч (утро 11-25), включая откат в течение минуты («добавь отступ перед C» → «не, верни как было»). Портинг в приложение гонял согласование макета («Стой, еще рано. Я еще не согласовал макет»). Счётчики по категориям были построены по спеке, затем обрезаны («уберем счетчик логов… не нужно считать и тратить perf») — и тот же обход counts оказался и CPU-спином, и плато live-check (одна непроверенная фича → сборка, два отладочных бис, откат в коммите 0d880c8). Ранняя спека несла QT-специфику до всякого решения стека («а причем тут QT поиск? Убери QT специфику»).

есть brainstorming для пайплайна. новое (a) гейт согласования макета: фидбэк вкуса собирается ТОЛЬКО на макете; до явного согласования — никакого апп-порта; никогда не переправлять откат без нового вопроса. (b) правило cost-flag спеки: любой критерий, стоимость которого масштабируется per-ряд/per-проб, помечен владельцу с perf-оценкой до имплементации. (c) никакие слова стек-имплементации в спеке до решения STACK.md. (И от владельца: батчить фидбэк одним раундом обзора, а не стримить.)

P10 · cwd- и окруженческие ловушки — тихие прогоны в неправильном контексте агент

Что: JS-гейты из корня репо тихо тестировали неверную среду (повторный прогон; пункт правила 7); beforeDevCommand Tauri сломал --prefix ui в момент scaffold; live-прогоны теряли headless.ts и PIPELINE.md по причине дрейфа cwd с «No such file or directory».

есть пункт правила 7 + ловушка в agent-brief. новое хук: на Bash-неудачу с «No such file or directory» по проектному пути печатать pwd и путь разрешения — делает весь класс самодиагностируемым.

P11 · Тулчейн расходится с убеждением агента (тихие опасные зоны) агент

Что: два эпизода одного типа, оба оплачены до того, как задокументированы: (a) macOS case-insensitive FS резолвит ./FiltersTab в filtersTab.ts → undefined-компонент; (b) vitest ничего не доказывает о типах TS, потому что esbuild срезает их (первопричина v0.2.0). Ни у одного нет canary-теста.

новое правило кита: каждое нагруженное допущение «X работает» (module resolution, type stripping, свежесть кэша) получает 1-строчный canary-гейт в первый день, до того как код начнёт полагаться на него.

P12 · Скилы не триггерятся — владелец спросил дважды агент

Что: 11-23 владелец дважды за одну сессию спросил, используются ли предписанные скилы («А ты пользовался /vvv-claude-kit:building-testable-apps?», «почему ты не пользуешься благами…»), затем вручную дистиллировал правила скилов в CLAUDE.md. Один вечер визуальной приемки был потерян из-за несрабатывания описаний.

есть правило 3. новое механический триггер, копия хука bd prime: инджект 3-строчного напоминания всегда, когда задача касается ui/ или бисес новой фичи. Сигнал «владелец спросил дважды» означает: описание-текст не сработает, сработает только хук.

P13 · Delegation и харнесс-отказы агент

Что: 9 отказов спавна на несуществующем override модели (model_not_found), один потраченный обзорный прогон; первый CI-гейт провалился из-за различий раннера (ubuntu GTK/webkit dev libs); один субагент ответил координатору по-китайски — правило языка не дошло до spawn-промптов.

новое правила делегации для кита: пиновать только проверенно-доступные имена моделей; однострочный пункт языка владельца в каждом spawn-промпте; первый запуск любого нового CI-воркфлоу на одноразовой ветке/теге до того, прежде чем вешать на него релизный тег.

Рекомендуемый режим работы с ИИ-агентами (вперёд)

  1. Каждый spawn-промпт содержит пять фиксированных полей: id бисеса + указатель brief; ≤3 файлов; точные команды гейтов; капа токенов/вызовов; контракт чекпойнта + контракт отчёта статуса. Что-то длиннее — сигнал недостающего контекста: пишите это в brief или бисес, а не в следующий промпт.
  2. Done = аутпуты. Принимать отчёт агента только с приложенными гейт-аутпутами; прогнать один точечный гейт самому для спот-чека перед закрытием бисеса.
  3. Фидбэк дизайна в батчах по макету; апп-порт стартует только по явному mock-апруву (один раунд обзора вместо 20 стрим-коррекций — 1.5-часовая churn-сессия стоила больше всего релизно-пайплайнового дня).
  4. Никогда не позволять агенту ждать фоновую работу; мониторинг — работа координатора или foreground Monitor — агент, полирующий 20 минут, платит весь контекст за каждый раунд при нулевом выходе.
  5. Смотреть за паттерном 429: при входе сессии или агента в полный гейт или бенчмарк — сначала чекпойнт. После любой немой остановки координатор сперва постит однострочный resume-статус.
  6. Любая повторная коррекция — кандидат в механизм. Когда та же коррекция появляется второй раз (heredoc, skill-триггер, зелёные клеймы), прекращать писать правила и писать хук/скрипт — мета-вывод этого отчёта.

Методология: паттерны добыты из транскриптов (249 сообщений владельца), сверены с воспоминаниями bd и правилами; каждое «что случилось» выше подкреплено датами и id бисесов в docs/notes/report-data-mistakes.md. Цитаты владельца сохранены дословно как доказательства.
