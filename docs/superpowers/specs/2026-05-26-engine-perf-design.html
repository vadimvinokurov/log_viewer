Проблема

Все операции поиска и фильтрации медленные на больших логах (6.4M+ строк). Python-циклы с побайтовым декодированием каждой строки доминируют в runtime. Поиск использует отдельный кодовый путь вместо переиспользования инфраструктуры масок.

Архитектурные решения

  1. Единая труба масок. Поиск, фильтр и пин проходят через _compute_filter_mask(). Разница только в потреблении маски: AND (фильтр), OR (пин), пересечение с filtered_indices (поиск).
  2. Всегда без учёта регистра. Параметр case_sensitive удаляется из Filter, Highlight, SearchState. Все операции всегда case-insensitive. Упрощает код, убирает ветвление в горячих путях.
  3. Буферный regex для plain и regex. Один re.finditer по всему _buf + np.searchsorted для маппинга позиций обратно на строки. Устраняет побайтовое декодирование.
  4. Cython для simple query. Per-line матчинг, который не может использовать буферный скан, проходит через _filter_cy.pyx с typed memoryviews. Прямой доступ к C-памяти, без Python slice-объектов.

Архитектура

Поток данных (единый)

Команда (:s, :f, :p, :h)
  │
  ▼
_compute_filter_mask(pattern, mode)  →  bool mask[n]
  │
  ├── Plain:  re.finditer(re.escape(pattern), _buf, IGNORECASE) + np.searchsorted
  ├── Regex:  re.finditer(pattern, _buf, IGNORECASE) + np.searchsorted
  ├── Simple: _filter_cy.compute_mask_simple(_buf, spans, ast)  [Cython]
  └── Line#:  single index set
  │
  ▼
  ├── Фильтр:    combined &= mask
  ├── Пин:       combined |= mask
  ├── Поиск:     matches = np.where(mask)[0] ∩ filtered_indices
  └── Хайлайт:   spans из mask для покраски
