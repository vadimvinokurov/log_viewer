Атрибуция на проект. Клиентский учёт logviewer2 за то же окно даёт ~4.9 k ходов (2 957 координаторских + 1 892 субагентских); 5 588 ÷ 4 877 ≈ 1.15 — то есть ~85–90 % трафика второго аккаунта за 3 дня — это этот проект. Точная разбивка невозможна: у legacy-плана нет ни токенов, ни привязки к сессиям, а повторы при 429 могли увеличить счётчик.

Деньги второго аккаунта. Баланс API: included 60 / allowance 60, период 11-04 → 12-04, purchased 0 — счёт нетронут, расход идёт внутри включённого плана. Но именно на этот счётчик (3 000 запросов за день) ложатся известные смерти 429: недельные лимиты у этого провайдера считаются в запросах не хуже, чем в токенах.

Для пересекающегося окна (сессии 11-25 после 08:10 UTC) количество запросов Ollama — 468 — практически совпадает с числом ходов тех же сессий по транскриптам (~472), и на втором аккаунте калибровка сходится с тем же коэффициентом (~1.15 c учётом других расходов): биллингометр считает один запрос на один ход ассистента. Два следствия для прежних выводов. (1) Клиентский «свежий input» оказался хорошим прокси для объёма, который бэкенд фактически биллингует как вход (~95 k у клиента против ~81 k у бэкенда за ход — расхождение ~15 %), но плохим прокси для кэша: реально из кэша читается почти всё. (2) Данные до 11-25 08:10 в долларах и токенах не покрыты (а на втором аккаунте токенов нет вовсе), — разделы 2–4 ниже анализируют транскрипты именно как «контекст-давление», не как счёт.

5. Рекомендации

Уже в правилах (продолжать применять)

CLAUDE.md 7Короткие ходы на чекпойнтах · промпты агентов указывают на docs/notes/agent-brief.md · числа вместо скриншотов · точечные гейты между шагами · лимитировать агентов · никаких heredoc-правок. Трактовка меняется: главный эффект этих правил на текущем бэкенде — меньше запросов, меньше латентность и меньше риск недельных лимитов 429 (см. паттерны P1/P7 в отчёте об ошибках), экономия рублей — вторична.

Новые, с учётом реального биллинга

  1. Держать разговор координатора малым — теперь ради латентности и окнных лимитов. /clear на границе задачи; задача = id бисеса, координатор читает бисес и резюме, а не файлы; крупные чтения — в агенты. Каждый лишний ход гиганта биллингуется на ~80 k входа и увеличивает ход по времени.
  2. Сокращать число запросов — главный счётчик денег. $1.44 за день при 468 запросах — то есть ~$0.003/запрос. Деградировавшие циклы (359 вызовов) и повторные гейты — прямое умножение запросов; «рубить цикл на третьем повторе» и «один полный гейт на чекпойнт» — денежные правила, не только эстетика.
  3. Не перечитывать файлы и картинки ради одной детали. Доминирующий избегаемый паттерн: 3–6 чтений того же файла (ipc.rs ×3, golden loaded.png ×6, uiConsole.ts ×4). Картинки в контексте — единственный вид payload, который бэкенд точно не отдаст из кэша.
  4. Подрезать фоновый шум. Диф экспорта beads и полные тексты хуков (см. using-skills) — фиксированные надбавки к каждому ходу; экспорт beads — на закрытии сессии, хук — в 5 строк.
  5. Калибровать ожидания по Usage API, а не по транскриптам. GET https://ollama.com/api/usage?range=24h|7d|30d с ключом из окружения (токены/доллары) и с ключом второго аккаунта из связки Keychain (только счётчик запросов; ключ в команды подставлять через переменную, никогда не печатать) — быстрая проверка факта перед любым решением о методах экономии; клиентские счётчики использовать только для поиска источников давления (какие файлы, картинки, циклы).

7. Рекомендуемый способ работы с агентами (ближайшие 30 дней)

  1. Координатор: граница задачи → /clear → bd ready → claim → бисес + brief + раздел спеки (один экран) → агент с промптом-указателем и бюджетом → резюме → один точечный гейт → закрыть бисес → коммит → конец хода.
  2. Агенты получают: id бисеса, указатель на brief, ≤3 файлов, точные гейт-команды, строку бюджета и инструкцию чекпойнта. Больше ничего inline.
  3. Бюджет задачи считать теперь в запросах и картинках: ≤ N запросов на задачу (для типовой задачи модуля — 30–60), ноль перечитываний одной картинки.
  4. Раз в день (или перед релизом) сверка с Usage API по обоим аккаунтам: usage_usd, request_count, доля кэша (текущий ключ) и request_count (ключ из связки). Резкий рост не-кэшированного входа = в контекст попал payload, который не кэшируется (картинки, новые большие файлы).

Методология: раздел 1 — прямо из Usage/Balance API Ollama Cloud (docs.ollama.com/api/cloud-usage), замер сделан 2026-11-25; текущий аккаунт метрируется с 08:10:34Z того же дня (доллары и токены), второй аккаунт (ключ прочитан из macOS Keychain при подготовке отчёта, в командах и файлах не печатался) отчитывается только счётчиком запросов. До утра 11-25 счётно только окно замера — сессии 11-22…24 измеряются клиентским учётом транскриптов (разделы 2–4). Клиентские «токены» и биллинг — разные шкалы; их нельзя складывать или сравнивать попозиционно. Полные таблицы майнинга транскриптов — docs/notes/report-data-tokens.md.
