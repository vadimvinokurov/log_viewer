Худшие: 24 подряд правки FUNCTIONAL_SPEC.html, 27× идентичная bash-обёртка live-check, 14× python3-heredoc правки live_check.mjs, 7× heredoc-борьба с дизайн-скриптом, 13× идентичный git show. 4. Рекомендации по сокращению расхода

Уже в правилах (продолжать применять)

CLAUDE.md 7Короткие ходы на чекпойнтах · промпты агентов указывают на docs/notes/agent-brief.md · числа вместо скриншотов · точечные гейты между шагами · капать агентов · никаких heredoc-правок. У каждого из шести пунктов в этих данных есть измеренный провал; у каждого — и измеренный успех (диапазон 40–60 k у хорошо проинструктированных модульных агентов). Они записаны как проза, а отчёт об ошибках показывает, что проза выветривается в длинных сессиях, — считайте их запасом, а механизмы — дефолтом (раздел ниже).

Новые, по ожидаемому эффекту

  1. Держать разговор координатора малым всегда. Это 85 %-й драйвер. Практически: /clear или новая сессия на каждой границе задачи; задача — это id бисеса, координатор читает бисес и возвращённое резюме, а не файлы; крупные чтения (целые файлы, документация, транскрипты) — в агенты. Средний координаторский разговор ~40 ходов при 95 k input обходится в ~4 M юнитов; та же работа с перезапуском на каждый чекпойнт стоила бы малую долю.
  2. Никогда не перечитывать файл ради одной детали. Доминирующий избегаемый Read-паттерн — 3–6 чтений того же файла (ipc.rs ×3, golden loaded.png ×6, uiConsole.ts ×4). Правило для координатора: файл читается один раз, нужный блок фиксируется в плане (описание бисеса), все последующие взгляды на файл делегируются агенту, владеющему изменением.
  3. Рубить циклы механически на третьей идентичной ошибке. 359 потерянных вызовов — это в основном циклы по 20–50 минут, которые «полная перезапись файла» закончила бы за 2 вызова. Именно правило, которое стоит хука, а не прозы: post-tool-use-страж, помечающий третий подряд вызов того же инструмента и требующий смены маршрута. См. отчёт об ошибках — три из верхних драйверов потерь имеют форму циклов.
  4. Картинки — только для визуальной приемки (уже правило 4); данные добавляют: и никогда не перечитывать один и тот же golden дважды; проценты диффа уже отвечают «изменилось ли», а текстовые диффы харнесса отвечают больше, чем повторное чтение.
  5. Подрезать фиксированную фоновую стоимость. Убрать диф экспорта beads на 20–33 КБ из контекста координатора (перенаправить шум bd в агентов или выставлять экспорт на закрытии сессии); держать малой системную часть координатора (меньше автозагружаемых скилов на сессию; хук using-skills кита добавляет полный текст правила в каждую сессию — сделайте этот хук на 5 строк, а не полный текст).
  6. Батчить гейты на естественных границах — среди ~397 гейт-вызовов есть повторные полные прогоны воркспейса с интервалом меньше часа. Паттерн чекпойнт-коммит сочетается с фиксированным одноразовым «полный гейт перед коммитом» (правило 9), а везде иначе — точечные однофайловые гейты.

6. Рекомендуемый способ работы с агентами (этот проект, ближайшие 30 дней)

  1. Координатор: граница задачи → /clear → bd ready → claim → прочитать бисес + brief + раздел спеки (максимум один экран) → запуск агента с промптом-указателем и бюджетом → получить резюме → прогнать один точечный гейт, чтобы поверить → закрыть бисес → коммит → закончить ход.
  2. Агенты получают: id бисеса, указатель на agent-brief, ≤3 файлов, точные команды гейтов, строку бюджета токенов и инструкцию чекпойнта. Больше ничего inline.
  3. Максимум два гейта за ход координатора; визуальные проверки через проценты диффа npm run e2e и дизайн-оракул; картинки — только когда нужно человеческое решение.
  4. Держать целевой диапазон агента 40–60 k; любой агент > ~100 k сырых токенов — процессный баг: остановить, забрать его заметки из bd update, разрезать бисес.

Методология: цифры usage взяты прямо из message.usage транскриптов; привязка сессий к задачам — по содержимому разговоров; оговорка о весах бэкенда — выше. Черновик майнинга с полными таблицами по 15 сессиям и профилем вызовов инструментов — docs/notes/report-data-tokens.md.
