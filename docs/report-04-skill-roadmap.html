Дорожная карта скилов vvv-claude-kit

Что создавать, что доделать в существующих скилах, чего не создавать вовсе — чтобы разработка приложений агентом стала дешевле и предсказуемее. Консолидация трёх отчётов проекта + инвентаризация самого кита. Каждая рекомендация несёт доказательство из реальных сессий; порядок — по (урон × частота) / цена. Сопутствующие отчёты: токены · ошибки агента · тестирование.

4. Версии существующих скилов (малые издания)

  1. building-testable-apps + строка гейтов: «перед закрытием кодовой задачи — один точечный гейт файла модуля; полный воркспейс — один раз перед коммитом» (расписание уже в токен-скиле; здесь — строка-указатель, чтобы конституция не заставляла гонять всё за каждым микроправкой).
  2. ui-development + visual-check-budget: не более одной картинки на решение; никогда не перечитывать ту же картинку; снимок по элементу вместо полного окна; PNG-чтение = только визуальная приемка.
  3. building-testable-apps + property-testing: в правило 4 (golden-корпус) добавить класс: компонент, смотрящий в произвольные пользовательские байты (парсер, декодер), обязан иметь property/fuzz-тест (произвольные байты → нет паники, нет зависания), когда такой компонент существует. Закрывает крупнейший тестовый пробел (инвентаризация §3.1).

5. Процесс принятия каждого нового скила

Скил без теста — неопробованная инструкция. Цикл (по superpowers:writing-skills, прецедент — ui-development):

  1. RED: свежий агент получает типовую задачу скила (например, «добавить компонентный вариант») без скила; записывается вербатим, как агент по умолчанию ведёт себя, — это и есть список провалов, под которье пишется документ.
  2. GREEN: тот же сценарий с текстом скила в контексте свежего агента; сверяется, что пайплайн воспроизведён, а не пересказан.
  3. REFACTOR: каждая лазейка/грань, выявленная прогоном, возвращается в скил (например, грань «новый рендер не имеет before» попала в таблицу ловушек именно прогона).
  4. Коммит скила с упоминанием прогона в сообщении — иначе не видно, что скил вообще кто-то проверил.

6. Чего создавать не надо

  • Дублей superpowers: TDD, планирование, отладка, мозговой штурм уже есть — вместо новых скилов решается триггеринг (хук, §3).
  • Проектные скилы: специфика одного репо (структура бисов, имена скриптов, порядок релизов) живет в CLAUDE.md и бисах проекта; скил кита — только то, что переезжает между проектами.
  • Зонтичные скилы: «testing»-скил в один документ, покрывающий RPC + goldens + live + benchmarks — не триггерится по описанию и читается наполовину; один скил = одна сессия-проблема.
  • Мотивационные документы вместо хуков: если требование должно выполняться никогда не наоборот (каждая картинка, каждый heredoc, тег-пуш), — это хук, а не пункт в документе.

Методология: консолидация рекомендаций трёх отчётов (report-02 §рекомендуемые механизмы, report-01 §6, report-03 §4 + §7) и инвентаризации текущего состояния кита (5 существующих скилов, 1 создан в этой сессии, 1 хук); каждая строка несёт доказательство — число или событие из транскриптов проекта. Приоритеты: (1)–(3) скилы тестового слоя, (6)–(7) релиз и экономика, хуки — параллельно.
