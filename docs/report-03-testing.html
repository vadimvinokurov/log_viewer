2. Coverage picture

Strong: the parser/engine path (layers 1+2+3+4) and the UI decision/state path (layers 5+6+8) both have layered, mostly redundant-in-a-good-way coverage; every UI state is both state-asserted (5) and pixel-accepted (8). This is what makes headless-first development real rather than rhetorical — the app was demonstrably verifiable without a screen across the whole v0.3 rewrite.

Weak: everything at the two ends of the funnel. Real-window checks (10) exist for recently-finished milestones only; benchmarks (11) have no regression gate; the design oracle (9) covers 3 elements; and the failure-visual states are barely present (one error.png golden, no loading/overflow state coverage).

3. Gaps, ranked by expected cost of staying unfilled

  1. No parse robustness testing — no fuzzing/property testing on the parser (the one component that faces arbitrary user bytes). 9 fixtures + 31 cases cover intended inputs only. A proptest (arbitrary bytes → no panic, no hang) is a few hours of work and removes an unbounded risk class.
  2. Live-check regression drift — verified flows lose their named checks as milestones pass. Recommendation: make the 14 → ~40 named checks permanent and additive; a milestone's live-check section never shrinks.
  3. No benchmark regression gate — measure always, fail never. Add --baseline prev comparisons in the release-gates script (per BENCHMARKS.md rows), not CI (needs test_logs).
  4. Design oracle decay — 3 pairs, no wiring. Every design frame should gain a ?show= variant + PAIRS entry at creation time, and the oracle runs before closing any visual task.
  5. Failure/empty/loading visual states — one error golden today. Empty file, load-failed, permission-failed, empty categories — each should be a state generator + golden, or the UI will be re-designed at first real error.
  6. Golden flake ownership — Chrome version/font drift can break all 43 locally. Cheapest fix: record the Chrome/OS version with each re-baseline note (PIPELINE §5) and keep threshold policy explicit; on drift, re-run once on a second machine before suspecting the code.
  7. Accessibility — aria incidentally present via standard components, but no tab-order/contrast/axe checks even for the app's custom rows and tabs. Low urgency for a personal tool, high leverage if this ships to others.

5. Recommended testing workflow with AI agents

  1. Agent writes the test first (TDD is in agent-brief): failing test → implementation → green module test. The test file is the agent's primary deliverable alongside the module.
  2. Layer map per task type: pure logic → layers 1/3/6; UI state → 5 (add a capability + uiConsole case); UI look → 8 (state generator + golden first, then implementation); cross-milestone regression → 10 (add a named check, keep old ones).
  3. Close a task only with its stated layer's evidence in the agent report — command outputs, not "all green" (mistakes P3).
  4. Milestone closure = live check (rule 5): the driver runs, its 14+ named checks are green, new checks from this milestone are added before the bead closes.
  5. Before a release: full gates + goldens + the design oracle + benchmark comparison vs the previous baseline — one script, run locally, then tag (mistakes P2's mechanism).
  6. Guard the two weak spots proactively: parser proptest land-glass (one-time effort) and the additive live-check list (habit) — both prevent regression classes the current strong layers cannot see.

Method: static enumeration (no suites were run for this report); counts from files and case definitions; verdicts cross-checked against the project's own bug records — which layers actually caught which classes, per bd memories, PIPELINE and the session transcripts.
